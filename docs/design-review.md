# Independent design review (2026-11-23)

Paths refer to the macOS checkout `<chromium checkout>`; the same relative paths exist in the Linux checkout.

**Verdict. Use native guest surfaces for ordinary cards and capture only the cards whose pixels a shader, recording, or rewind actually needs.** Darc already computes a CSS transform for each real guest. Showing that element lets Viz aggregate the guest’s latest submitted frame directly into the display, eliminating the capture request, delivery to JS, texture import, and second presentation through the scene canvas. It also preserves native input for the focused page. A second surface layer is worthwhile only when the same guest must appear twice. Perspective, masks, or opacity can still force an intermediate render pass, and independently composited DOM cannot share WebGL’s per-fragment depth buffer. Keep the texture route for those cases. Native composition removes a round trip. It cannot guarantee 64 independently rasterizing pages at 60 Hz. Darc’s current layering · Blink guest surface · Viz pass-merging conditions

### What the traces establish

- **Linux needs a trace of the final direct route.** The often-quoted 0.4–0.6 ms consumer cost came from I420/NV12 tracks at N=32. An earlier direct-route trace at N=64 instead attributed about 6% of wall time to copies, 4% to embedder WebGL, 34% to guest raster, and roughly 30% to task overhead. Those runs had different delivery rates and pipeline depths. Measure exclusive CPU time per **presented scene frame**, with equal producer cadence and guest content across routes. Track trace · Direct trace
- **Mac has two distinct GPU-process costs.** In the hardened direct trace, guest command buffers occupied 85% of wall time on `CrGpuMain`; copies occupied 6% on `CompositorGpuThread`. Patch 10 shares a token per **GPU-task flush**. Each RGBA copy still calls `FlushAndSubmitCopyOutput`, which flushes and can submit Graphite work. The reported Mac submission counts are patch 09, and DPR changed between rounds. Count actual Metal submissions by thread and guest frame ID at fixed DPR on patch 10, with GPU timestamps to distinguish device execution from CPU submission and waits. Mac trace and display change · Token batching · Remaining flush
- **The latency probe ends too early for the product question.** The painted timestamp is decoded by JS. It excludes the scene’s subsequent draw and presentation, and asynchronous readback adds its own scheduling. One-vsync steps suggest a missed deadline but do not locate it. Correlate the same guest frame through activation, aggregation, copy completion, JS consumption, and scene presentation feedback. Latency methodology

### Direct-route correctness and security

- **Authorization is narrower in JS than in the browser.** The broker binds the host for frames generally. Browser validation checks caller process, exact parent RFH, outer delegate, and generic guest status. Those checks reject ordinary iframes and unrelated embedders, but omit Controlled Frame capability, guest subtype, and the screenshot restriction checked by the existing capture API. Enforce all three browser-side. An authorized capture includes cross-origin descendants’ visible pixels. Viz blacks secure-output-only textures in copy passes; preserve that rule in any fast path. Binder · Ownership check · Policy precedent · Redaction
- **The “per-document” quota does not count a document’s sources.** Each Blink source binds a fresh host. Each host counts its own receiver set. One permitted 8192² × 16 RGBA allocation already requests 4 GiB before overhead. Account for aggregate bytes and outstanding requests on the document and process, including still-held frames. The browser currently checks only the slot index before issuing another copy. Fresh binding · Quota · Slot check
- **Close and failure retain resources.** `close()` drops the source remote but retains imported slot images and ready frames. `read()` can subsequently return a ready frame. `End()` also leaves the source remote and capture handle alive. Viz retains per-source damage keys until sink cleanup and has no source-close cancellation for parked requests. Release unused slots and keys immediately while allowing already-delivered `VideoFrame`s to finish. Read and close · End · Viz cleanup
- **Revocation occurs only when issuing a copy.** A request can stay parked, targets a non-exact surface, and accepts success without another owner check. This leaves a potential disclosure window **if** a sink survives an ownership transition. I found no demonstrated cross-embedder leak. Since the destination is already exported, revocation must prevent the write itself. Normal guest removal, cross-site navigation, and renderer crash have tests. GPU-process loss has no corresponding source observer or ring recreation; retries reuse the old images. Issue and completion · Existing lifetime coverage
- **Sync is configuration-dependent.** The default path passes creation, write-ready, and reader-release tokens. With automatic token management enabled, `GetSyncTokensForDisplayCompositor()` ignores the explicit reader token and consults the browser image wrapper’s token map. The patch never transfers the renderer’s release dependency into that map. Fix this before enabling the feature. Also attach the final consumer fence to image destruction when the source disappears while frames are held. Explicit token path · Token selection · Weak release callback
- **Two freshness bugs affect normal use.** A forced redraw coinciding with genuine descendant-only damage can suppress the final video update because the parent frame index is unchanged. Separately, automatic backpressure and explicit `setFrameRate` overwrite the same sink entry, so closing one source can clear another client’s limit. Track real subtree damage separately from forced redraws and give each rate request an owner. Damage suppression · Throttle cleanup · Shared sink entry

**API recommendation.** Standardize one pixel-export operation on the owned element, `await frame.captureStream({video: {width, height, frameRate}, audio: false})`, returning a video `MediaStreamTrack` via its stream. A worker can consume the track through `MediaStreamTrackProcessor` as a bounded stream of closeable `VideoFrame`s. Specify latest-frame delivery, final damage after throttling, source timestamps, revocation, and end/error behavior. Keep producer cadence a separate presentation hint because it also affects native display and other readers. Choose buffer format and transport internally. For MPArch, bind capture to the browser-validated guest page/root sink and follow its replacement on navigation. A whole-WebContents fallback could capture the shell. HTML-in-Canvas deliberately omits readback-capable painting of remote layers, Element Capture restricts an existing capture track, and neither draft WebGL video-texture extension is registered in this build. MPArch guard · Remote painting · Element Capture · WebGL2 extension registry

**First three experiments, in order**

1. Run native-only, native-plus-eight-shaders, and all-texture walls at N=64/128 with identical guest cadence, DPR, card geometry, and camera motion. Include canvas, ordinary DOM, and video. Record presented scene p99, focused input-to-present, and capture copies per second.
2. At fixed producer rate, trace a numbered guest frame from submission to presentation on both platforms. Compare native, copy with immediate release, and copy plus scene sampling. This isolates the latency boundary and prices the consumer independently.
3. Cross producer scale 1×/½× with copy scale 1:1/2:1 and mipmapped/bilinear sampling. Record actual tile and pass dimensions, submissions, CPU/GPU time, and text quality. That result decides whether to invest in producer scaling, the sampling fix, or direct-to-slot rendering.
